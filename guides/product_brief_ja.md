# Kapsaro: `.env` を暗号化して Git で共有する

Kapsaro は、暗号化した秘密情報を Git で共有する、オフライン優先の CLI ツールです。`.env` 形式のキーと値、証明書、秘密鍵ファイル、設定ファイルなど、任意のバイナリデータを扱えます。秘密情報の変更、メンバー管理、鍵更新を、コードと同じ Pull Request（PR）の手順でレビューできます。

<a id="導入判断の要点"></a>
## 適する用途と限界

Kapsaro は、Git と PR レビューを使う小規模〜中規模のチームに適しています。平文での秘密情報の受け渡しをやめ、ローカル開発、オフライン作業、CI/CD を共通の手順で運用できます。専用 SaaS や常時稼働するサーバーは不要です。

秘密情報の追加・更新とメンバー変更は、Git の差分で確認できます。Kapsaro は、標準的な公開鍵暗号方式である HPKE を使い、ファイルごとのマスター鍵を受信者それぞれに向けて暗号化します。データの暗号化には、マスター鍵から導出した鍵を使います。メンバー変更時には受信者を現在のメンバー構成へ同期でき、開示履歴から値の交換が必要かを判断できます。

すでに開示された平文の回収や、受信者による複製の防止はできません。組織全体のポリシー管理、細かなアクセス制御、実行時に渡す秘密情報の一元管理には、別の仕組みが必要です。

<a id="よくある課題"></a>
### この運用で扱う課題

<a id="チャットや手作業で-env-を配布している"></a>
<a id="envexample-と手作業でのシークレット受け渡し"></a>
平文での受け渡しでは、チャット履歴や端末に秘密情報が残り、離脱したメンバーの手元にも残り続けます。最新版や変更者の把握も難しくなります。`.env.example` で必要なキーを示していても、参加時には別途資格情報を集める必要があります。キーの追加・名称変更・更新が漏れると、staging や CI だけで設定の違いによる障害が起きることもあります。

<a id="専用のシークレット管理サービスは運用が重い"></a>
専用サービスには、サーバー保守、権限設計、常時接続が必要になる場合があります。小規模チームには導入・維持の負担が大きく、変更の手順も Git レビューから分かれることがあります。

<a id="暗号化するだけでは残る運用課題"></a>
暗号化を導入しても、鍵と受信者の変更レビュー、承認の記録、離脱メンバーが取得できた値の確認、CI 用資格情報の管理は必要です。Kapsaro はこれらをリポジトリの変更として扱います。チームでのレビューと資格情報の失効手順もあわせて整えてください。

<a id="他の選択肢との比較使い分け"></a>
### 他の方式との使い分け

| 要件 | 検討する方式 |
| --- | --- |
| `.env` の暗号化と実行時の環境変数への設定 | Kapsaro、またはこの用途に特化したツール |
| 既存の鍵管理基盤や外部の鍵管理サービスとの連携 | 必要な鍵管理方式に対応するファイル暗号化ツール |
| 組織全体のポリシー適用、SSO、SCIM、細かな ACL | 一元管理型のシークレット管理サービス |
| Git と PR で秘密情報やメンバーの変更をレビュー | Kapsaro |
| 小規模〜中規模チームでの `.env`、証明書、CI 読み取り、鍵更新、開示履歴の管理 | Kapsaro |

<a id="典型的な導入フロー"></a>
## 導入手順

### 前提条件

- Ed25519 SSH 鍵
- Git リポジトリ
- 公開鍵とアカウントの対応を確認する場合は GitHub アカウント
- PR レビューや保護ブランチなど、メンバー変更を確認する Git 運用
- CI/CD を利用する場合は、安全に管理された CI のシークレット変数

### 既存プロジェクトへの導入手順

次の例は、Homebrew でインストールしてワークスペースを作成する手順です。初期化はリポジトリのルートディレクトリで実行してください。以後、リポジトリ内でコマンドを実行すると、既存のワークスペースが自動検出されます。ほかのインストール方法は[ユーザーガイド](user_guide_ja.md)を参照してください。

```bash
# Kapsaro をインストールする
brew tap ebisawa/kapsaro
brew install kapsaro

# ワークスペースを作成する
kapsaro init --member-handle alice@example.com

# 既存の .env を取り込む
kapsaro import .env

# 秘密情報を表示せずに復号を確認する
kapsaro run -- true
```

`.kapsaro/` を Git にコミットし、元の平文ファイルはリポジトリに含めないようにしてください。以後の変更と読み取りには、`set`、`get`、`run`、`encrypt`、`decrypt`、`rewrap` を使います。

<a id="kapsaro-が提供するもの"></a>
## 日常操作

<a id="1-平文をコミットせずに-env-を-git-管理できる"></a>
### キー単位で値を更新する

```bash
kapsaro set DATABASE_URL "postgres://..."
kapsaro set API_KEY "sk-..."
```

ここで示す値は例示用です。実際の秘密情報は、シェル履歴やコマンド引数に残さないよう、[秘密情報の入力手順](user_guide_ja.md#secret-input)に従って入力してください。

`.env` の各キーは個別に暗号化されるため、Git の差分で変更された項目を確認できます。電子署名は文書全体を対象にするので、異なるキーの変更でも署名などの共通行が更新されます。マージで競合した場合は、[正常な文書に変更を再適用する手順](user_guide_ja.md#git-conflict-resolution)に従って解消してください。

<a id="2-証明書やバイナリファイルも同一フローで共有できる"></a>
### ファイルを暗号化・復号する

```bash
kapsaro encrypt certs/ca.pem
kapsaro decrypt ca.pem.encrypted --out certs/ca.pem
```

証明書、設定ファイル、その他のバイナリファイルも、キーと値のストアと同じワークスペースで管理し、共通の暗号化・署名方式で保護します。

<a id="3-平文-env-を配布することなくアプリを起動できる"></a>
### アプリの起動と値の読み取り

```bash
kapsaro run -- docker compose up
kapsaro run -- npm start
kapsaro run -- rails server

kapsaro get DATABASE_URL
kapsaro get API_KEY
```

`kapsaro run` は値を復号し、環境変数として子プロセスに渡して、指定したコマンドを起動します。子プロセスには `PATH` や `RUST_LOG` など親の環境変数も引き継がれますが、親から継承する `KAPSARO_` で始まる変数は除去されます。子プロセスは復号した値を読み取り、外部へ出力できます。`kapsaro get` は値を表示するため、端末への表示が適切な場面で使ってください。

`-n` で名前付きストアを選択できます。

```bash
kapsaro set -n staging DATABASE_URL "postgres://staging/..."
kapsaro run -n prod -- ./deploy.sh
```

`dev`、`staging`、`prod` などの名前は、ワークスペース内の値を整理するためのものです。受信者はワークスペース単位で管理します。環境ごとに共有相手を変える場合は、[ワークスペースを分けてください](user_guide_ja.md#workspace-sharing)。

## メンバーと公開鍵の管理

<a id="4-メンバーの参加と承認を-git-レビューに統合できる"></a>
### メンバーを追加する

```bash
# 新メンバー: 参加申請を作成する
kapsaro join --member-handle bob@example.com

# 既存メンバー: 申請を確認して受信者を更新する
kapsaro rewrap
```

新メンバーは、まず承認待ちの `incoming` として登録されます。申請を Git で共有し、既存メンバーがレビューします。そのメンバーが `rewrap` を実行して申請を承認し、ワークスペースの `secrets/` 配下（標準構成では `.kapsaro/secrets/`）の暗号化ファイルを更新します。メンバー変更はリポジトリの差分に現れ、PR で確認できます。

参加手順は、メンバー情報と更新した暗号化ファイルをともにコミット・共有し、新メンバーの端末で復号を確認するまでを含みます。既定のディレクトリ以外に保存したファイルも含め、[メンバー変更の完了確認](user_guide_ja.md#membership-completion)を参照してください。

<a id="8-メンバーの公開鍵の正当性を検証できる"></a>
### 公開鍵を検証・承認する

```bash
# active メンバーの鍵を GitHub と照合し、ローカルで承認する
kapsaro member verify --approve

# ローカルの信頼記録を確認・管理する
kapsaro trust keys list
kapsaro trust keys remove <kid>
kapsaro trust recipients list
```

有効な署名は、署名鍵がその文書に署名したことを示します。その鍵が名乗っている本人のものかは、別途確認が必要です。`member verify --approve` はメンバーの公開鍵を GitHub と照合し、確認操作を経て、承認した鍵をローカル信頼ストアに記録します。ここで確認するのは鍵と申告された GitHub アカウントの対応であり、そのアカウントが誰のものかはチームで確かめます。信頼ストアは承認した鍵や受信者の組を保存し、後の照合で予期しない変更を検出するために使います。`<kid>` は鍵の識別子です。

公開鍵の承認と参加申請の承認は別の操作です。参加申請の承認と受信者の同期は `rewrap` が担当し、`member verify --approve` はローカルに鍵の承認を記録します。

<a id="5-メンバー離脱と鍵の更新を機械的に実行できる"></a>
### メンバーの除外と鍵の更新

```bash
kapsaro member remove old-member@example.com
kapsaro rewrap
```

`rewrap` は、暗号化ファイルの受信者を現在のメンバー構成に同期します。既定の対象はワークスペースの `secrets/` 配下です。別の場所にある暗号化ファイルは `--target` で指定します。

- `kapsaro rewrap --rotate-key` は新しいマスター鍵を生成し、データを再暗号化します。メンバーの公開鍵と秘密鍵は変わりません。
- `kapsaro rewrap --clear-disclosure-history` は、影響を受けた秘密情報の値を交換した後に開示の記録を消去するために使います。記録の消去で資格情報が失効したり、過去の開示が取り消されたりすることはありません。
- `kapsaro rewrap --target <path>` は処理対象のファイルを指定します。

メンバーの鍵を交換する場合は、[鍵更新と検証の手順](user_guide_ja.md#new-key-verification)に従ってください。受信者の同期、ファイルのマスター鍵更新、メンバーの鍵ペアの交換は、それぞれ目的が異なります。

<a id="6-開示履歴を可視化しローテーションが必要な値を把握できる"></a>
### 離脱時に開示履歴を確認する

Kapsaro は除外された受信者を記録し、暗号化したキーと値のストアでは、その受信者に開示された可能性のある項目も追跡します。この記録は値の交換を検討するための情報であり、実際に読まれたかどうかを示すものではありません。

受信者の除外は、更新した暗号化ファイルに反映されます。以前に復号した値や古い暗号化ファイルは、引き続き利用される可能性があります。離脱時には暗号化ファイルを更新・共有し、共有したコミットからの利用を確認するとともに、影響するトークンやパスワードを発行元サービスで失効・再発行してください。詳細は[メンバー管理の手順](user_guide_ja.md#6-メンバー管理)を参照してください。

<a id="7-cicd-環境で-ssh-鍵やエージェントなしに動作する"></a>
## CI/CD

Kapsaro は、メンバーの秘密鍵をパスワードで保護した持ち運び用の形式に出力できます。

```bash
# 開発端末で CI メンバーの秘密鍵を書き出す
kapsaro key export --private --member-handle ci@example.com --out ci-key.txt
```

書き出した鍵を `KAPSARO_PRIVATE_KEY`、保護用のパスワードを `KAPSARO_KEY_PASSWORD` として CI のシークレット変数に登録します。CI 上で SSH 鍵、SSH エージェント、ローカル鍵ストアを用意せずに `run` や `get` を使えます。ジョブで利用する前に CI メンバーの登録を完了し、共有したファイルを復号できることを確認してください。

CI ボットにも人間と同じメンバー管理の規則を適用します。CI メンバーを除外して `rewrap` を実行すると受信者が更新されます。CI 資格情報の廃止・漏洩時には、ボットが取得できた秘密情報の失効・交換も必要です。

共有範囲はワークスペース単位です。CI 専用のワークスペースには必要な秘密情報だけを置き、その情報を必要とする信頼できるビルドステップだけに資格情報を渡してください。バージョンを固定したインストール、ビルド来歴の検証、信頼に関する前提条件、復号確認は [CI セットアップ](user_guide_ja.md#ci-setup)を参照してください。
